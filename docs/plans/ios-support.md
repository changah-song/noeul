# Plan: iOS support

*Brainstorm, 2026-10-21. Nothing here is decided. Paths are relative to the repo root.*

## Recommendation / first step

- **The JS app is mostly portable; the reader is not.** Almost every screen is
  plain React Native + Expo modules that already run on iOS. The blocker is the
  ~17k lines of Kotlin in `frontend/modules/` — above all the native EPUB reader
  (`NativeEpubReaderModule.kt` 3.9k lines, `EpubPageView.kt` 3.1k lines), which
  *is* the product. Without it, iOS shows `read.nativeReaderAndroidOnly`
  (`modules/native-epub-reader/src/NativeEpubReaderView.js:158`).
- **Key decision:** port the reader to Swift (TextKit 2 / Core Text, matching
  the Kotlin feature-for-feature) **or** replace both platforms with one shared
  renderer (WebView-based EPUB, or a Skia/RN-rendered paginator). A Swift port
  doubles maintenance of the most-changed code in the repo; a shared renderer is
  a rewrite of Android too. Recommend a 1–2 week spike of each on one chapter
  before committing.
- **Ship the screen OCR overlay as Android-only.** iOS does not allow drawing
  over other apps or capturing the screen from the background. Offer a reduced
  iOS alternative (screenshot / photo / share-sheet OCR via Apple Vision).
- **First step:** delete and regenerate the stale `frontend/ios/` folder
  (it is an SDK 50 / RN 0.73 prebuild under the old `FluentFable` name, see
  `frontend/ios/Podfile.lock`), get the app to boot in the iOS simulator with
  the reader stubbed, and list every screen that breaks. That is a 1–2 day
  task and turns this plan's guesses into a real list.

### Things the Kotlin reader does that a port must match

Inventory these before estimating (grep `EpubPageView.kt`):
- Korean line breaking with invisible joiners (`src/koreanLineBreak.js`,
  `hasTokenBoundary` in `NativeEpubReaderModule.kt:3494`) — iOS `NSLineBreak`
  rules for Korean differ; test early.
- Per-language text locale (`NativeEpubReaderModule.kt:1341`).
- Ruby row spacing for pinyin and gloss (`annotationSpacePx`,
  `PINYIN_ROW_SCALE`).
- Level underlines with dissolve animation, saved-word pixel fades (`SAVED_FADE_MS`).
- Hit-testing a tap to a word / CJK token (`hitTestText`, `markedCjkWordAt`).
- Focus mode imperative navigation (`focusNav`), page snapshots, themes, fonts
  loaded from assets (`loadReaderSansTypeface`).
- Event contract with JS (`NativeEpubReaderView.js`): the Swift module must emit
  the same event names and payloads so `screens/Read.js` needs no changes.
  Write this contract down as a TypeScript type first.

## Cross-platform JS issues

- **Toasts:** `ToastAndroid` is used in `screens/Read.js:774,3420`,
  `components/Songs/SongReader.js:214`, `components/shared/VocabLevelModal.js:164`,
  `components/shared/WordCheckModal.js:392`. On iOS it is undefined and will
  crash. Add a small `services/toast.js` with an in-app toast for iOS.
- **Hardware back:** `BackHandler` in Read, Home, Learn, Write, Onboarding,
  SongReader. No-op on iOS, so every screen that relies on it to close a sheet
  or leave the reader needs a visible close button or swipe-back. Audit each
  listener.
- **Notifications permission:** `Read.js:3538` asks `POST_NOTIFICATIONS` for the
  listen player. iOS lock-screen controls need no notification permission.
- **Keyboard:** `KeyboardAvoidingView` already switches `padding` on iOS in
  Auth, Write, Home, BeforeYouGoSheet — test anyway.
- **Safe areas:** ~24 uses of `SafeAreaView`/`useSafeAreaInsets`. Check the
  floating Read/Learn pill (commit 9f4e880) against the home indicator and
  Dynamic Island.
- **Fonts:** Inter / Fraunces / Noto Serif KR via `@expo-google-fonts` work on
  iOS. The reader's own fonts live in the native module's assets and must be
  bundled for iOS too. Chinese falls back to PingFang (fine) instead of Noto.
- **Haptics:** `services/haptics.js` uses `expo-haptics`; iOS haptics are
  stronger — review intensity.
- **File picker:** `expo-document-picker` works on iOS; EPUB UTI needs
  `org.idpf.epub-container`. Consider "Open in Noeul" (document types in
  `Info.plist`) so books open from Files/Mail.
- **TTS:** `react-native-tts` supports iOS (AVSpeechSynthesizer).
  `services/listenPlayer.js` filters voices with Samsung naming
  (`voiceGender`, `-language$` alias) — rewrite the iOS branch to use
  `AVSpeechSynthesisVoice` quality (enhanced/premium) and identifiers.
  Pronunciation audio (`services/pronunciationAudio.js`, expo-av) is fine;
  note `expo-av` is deprecated in SDK 54 — move to `expo-audio` on both.
- **Local SQLite / bundled DBs:** `expo-sqlite` works; `assets/data/hanja.db`
  (14 MB) and `zh_characters.db` copy via `expo-asset` on both platforms.
- **Telemetry:** `services/appTelemetry.js` already records `Platform.OS`.

## Expo / EAS / App Store setup

- Apple Developer Program ($99/yr), App Store Connect app record, bundle ID
  `com.noeulapp.Noeul` registered.
- EAS: let EAS manage certificates and provisioning; add `submit.production.ios`
  (ASC app ID, team ID). Add an `ios` simulator profile
  (`"ios": { "simulator": true }`) for development builds.
- `app.json` additions: `ios.infoPlist` (camera/photo usage strings if OCR uses
  photos, `UIBackgroundModes: ["audio"]` for listen mode,
  `ITSAppUsesNonExemptEncryption: false`), `usesAppleSignIn: true`,
  Google sign-in URL scheme, `supportsTablet` (decide: iPad means the reader
  must handle wide/landscape layouts — consider `false` for v1).
- Privacy manifest (`PrivacyInfo.xcprivacy`) for required-reason APIs
  (UserDefaults via AsyncStorage, file timestamps). Expo SDK 54 can generate it
  from `ios.privacyManifests`.
- App Store listing: screenshots for 6.9" and 6.5" iPhone (and iPad if
  supported), privacy nutrition labels (Supabase auth email, usage telemetry,
  user content sent to the API for AI explanations), age rating.
- App Review risks: the "Read anywhere" OCR feature must not be advertised on
  iOS; bundled public-domain books are fine; AI features need no special
  disclosure but a content report path is wise.

## Testing setup

- Requires a Mac with Xcode (the dev machine already is one). iOS Simulator for
  daily work; one physical iPhone for TTS voices, haptics, background audio,
  and performance (simulators lie about all four).
- Development build via `eas build --profile development --platform ios` or
  local `npx expo run:ios`.
- Jest tests are platform-neutral; add a few `Platform.OS = 'ios'` cases for
  the toast and back-navigation fallbacks.
- The `pr-check` skill is Android/phone-only; it would need an iOS lane
  (simulator smoke test with `xcrun simctl`) or stay Android-only with manual
  iOS checks before releases.

## Risks

- **Reader parity drift.** Every reader feature after the port lands twice.
  The git log shows the reader changes almost weekly (fades, listen mode,
  focus mode, pinyin). This is the main argument for a shared renderer.
- **Korean/Chinese line breaking and ruby on TextKit** can eat weeks.
- **OCR is a headline Android feature** with no iOS equivalent; marketing and
  onboarding must differ per platform.
- **Background listen mode**: iOS suspends apps aggressively; TTS-in-background
  only works with an active audio session.
- **Old architecture**: `newArchEnabled: false`. Fine on SDK 54, but new Expo
  modules in Swift should be written so they work on both (Expo Modules API
  handles this).

## Phased plan (rough effort, one developer)

1. **Boot (1 week).** Regenerate `ios/` via prebuild, simulator build, fix
   crashes (`ToastAndroid`, back handling), stub reader. Sign in with Apple +
   Google working against Supabase.
2. **Reader spike (2 weeks).** One chapter of a Korean and a Chinese book in
   (a) Swift TextKit 2 and (b) a shared renderer prototype. Measure: page-turn
   latency, tap accuracy, ruby rows, line breaks. Decide.
3. **Reader port (6–10 weeks if Swift; longer if shared renderer, but
   Android benefits).** Pagination, underlines, fades, taps, focus mode,
   songs reader, PDF via PDFKit.
4. **Listen mode on iOS (1–2 weeks).** AVSpeechSynthesizer queue, Now Playing
   controls, background audio.
5. **iOS OCR v1 (1–2 weeks).** Photo/screenshot OCR with Vision inside the app;
   Share Extension later (another 1–2 weeks; extensions need their own target
   and memory budget).
6. **Store prep and TestFlight (1–2 weeks).** Privacy manifest, listing,
   screenshots, TestFlight beta, review.

Total: roughly 3–5 months to a parity-minus-overlay iOS release.
